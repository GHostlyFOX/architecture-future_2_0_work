## Выявленные проблемы

### 1. Монолитное хранилище данных (DWH)

**Описание проблемы:**
Все корпоративные данные хранятся в единой DWH на базе устаревшего SQL Server 2008. Это создает единую точку отказа и узкое горло для всей аналитической работы компании.

**Затронутые бизнес-сценарии:**
- ⏱️ Построение отчётности занимает часы (вместо секунд/минут)
- 🚫 Блокировка развития новых направлений из-за необходимости вносить логику в DWH
- 💰 Задержки в принятии управленческих решений
- 📊 Невозможность self-service аналитики для бизнес-пользователей
- 🔄 Длительный time-to-market для новых отчетов и метрик

**Бизнес-impact:**
- Потеря выручки из-за неоперативных решений
- Снижение конкурентоспособности
- Рост операционных затрат на поддержку

---

### 2. Низкая производительность аналитических процессов

**Описание проблемы:**
Формирование сложных отчётов занимает часы. Объём данных измеряется сотнями терабайт, а множество сценариев использования приводит к большому количеству трансформаций.

**Затронутые бизнес-сценарии:**
- 📉 Невозможность оперативного мониторинга KPI
- 🏥 Задержки в получении медицинской статистики для принятия решений
- 💳 Медленная подготовка финансовой отчётности
- 🤖 Замедление работы AI-сервисов из-за долгой подготовки данных
- 👥 Низкая продуктивность аналитиков и менеджеров

**Бизнес-impact:**
- Снижение качества медицинских услуг
- Риски несоблюдения регуляторных требований (своевременная отчетность)
- Потеря клиентов из-за медленных финтех-сервисов

---

### 3. Отсутствие доменной изоляции

**Описание проблемы:**
Все направления (медицина, AI, финтех, корпоративные функции) тесно связаны через общую DWH. Нет четких границ между доменами, что затрудняет независимое развитие.

**Затронутые бизнес-сценарии:**
- 🔧 Изменения в одном домене влияют на другие (риск breaking changes)
- 👨‍💼 Невозможность автономной работы команд
- 🌐 Сложность интеграции новых бизнес-направлений (фармкомпании, производители оборудования)
- ⚖️ Конфликты приоритетов между доменами за ресурсы DWH
- 🔐 Сложность управления доступом к данным разных доменов

**Бизнес-impact:**
- Замедление инноваций
- Высокий time-to-market для новых продуктов
- Риски при масштабировании бизнеса

---

### 4. Устаревший технологический стек

**Описание проблемы:**
SQL Server 2008 (15+ лет), PowerBuilder (устаревший UI), старая версия Apache Camel. Технологии не поддерживают современные паттерны работы с big data и cloud-native подходы.

**Затронутые бизнес-сценарии:**
- 💸 Высокие затраты на поддержку устаревшего оборудования
- 🛡️ Риски безопасности (устаревшие патчи, уязвимости)
- 📱 Плохой UX для операторов клиник (PowerBuilder)
- 🔄 Сложность найма специалистов по устаревшим технологиям
- ☁️ Невозможность использования облачных преимуществ (масштабирование, отказоустойчивость)

**Бизнес-impact:**
- Рост TCO (Total Cost of Ownership)
- Снижение удовлетворенности сотрудников
- Технологический долг

---

### 5. Отсутствие self-service портала данных

**Описание проблемы:**
Бизнес-пользователи не могут самостоятельно создавать отчёты и получать необходимые срезы данных. Все запросы идут через IT-отдел или ограниченную BI-систему.

**Затронутые бизнес-сценарии:**
- 📊 Длинная очередь на создание отчетов через IT
- 🎯 Невозможность быстро проверить гипотезы
- 📈 Бизнес зависит от доступности технических специалистов
- 🔍 Нет прозрачности доступных датасетов и их качества
- 🚀 Замедление data-driven принятия решений

**Бизнес-impact:**
- Потеря конкурентных преимуществ
- Снижение гибкости бизнеса
- Неэффективное использование данных как актива

---

### 6. Смешение операционных и аналитических данных

**Описание проблемы:**
В DWH находятся как операционные данные (медицинские карты, истории болезней), так и аналитические. Операционные медицинские данные не нужны для аналитики, но занимают место и усложняют систему.

**Затронутые бизнес-сценарии:**
- 🏥 Риски утечки чувствительных медицинских данных
- ⚖️ Сложность соблюдения требований регуляторов (152-ФЗ, GDPR)
- 💾 Неэффективное использование хранилища
- 🔐 Усложненное управление доступом
- 🐌 Снижение производительности из-за большого объема неиспользуемых данных

**Бизнес-impact:**
- Юридические риски и штрафы
- Репутационные риски
- Избыточные затраты на хранение

---

### 7. Недостаточная масштабируемость инфраструктуры

**Описание проблемы:**
On-premise инфраструктура не позволяет быстро масштабировать ресурсы при росте нагрузки. Планируется интеграция фармкомпаний и производителей оборудования, но текущая система не готова.

**Затронутые бизнес-сценарии:**
- 📈 Невозможность обработки пиковых нагрузок
- 🌍 Планы географического расширения затруднены
- 🤝 Сложность подключения партнеров и поставщиков
- 💰 Капитальные затраты на расширение инфраструктуры
- ⏰ Длительное время provisioning новых ресурсов

**Бизнес-impact:**
- Ограничение роста бизнеса
- Упущенные возможности M&A
- Высокий CAPEX

---

### 8. Отсутствие centralized governance для данных

**Описание проблемы:**
Нет единого каталога данных, отсутствуют стандарты качества данных, не прослеживается линейдж (откуда пришли данные, как трансформировались).

**Затронутые бизнес-сценарии:**
- ❓ Пользователи не знают, какие данные доступны
- 🔍 Сложность поиска нужных датасетов
- 🎯 Низкое доверие к качеству данных
- 🐛 Сложность диагностики проблем в данных
- 📋 Трудности с audit trail для регуляторов

**Бизнес-impact:**
- Дублирование работы аналитиков
- Ошибочные решения на основе некачественных данных
- Compliance риски

---

### 9. Тесная связанность через шину данных (Apache Camel)

**Описание проблемы:**
Интеграция через старую версию Apache Camel создает tight coupling между системами. Изменения в одной системе требуют изменений в шине и других системах.

**Затронутые бизнес-сценарии:**
- 🔄 Сложность внесения изменений (ripple effect)
- 🐌 Медленная разработка новых интеграций
- 🛠️ Высокая стоимость поддержки
- 📉 Снижение надежности (один упавший consumer может блокировать всех)
- 🔧 Сложность troubleshooting проблем интеграции

**Бизнес-impact:**
- Увеличение TTM (Time-to-Market)
- Рост технического долга
- Снижение гибкости

---

### 10. Недостаточная безопасность и compliance

**Описание проблемы:**
При работе с медицинскими данными (152-ФЗ) и финансовыми данными (требования ЦБ РФ, ПДн) требуется строгий контроль доступа, аудит, шифрование. Текущая архитектура не обеспечивает необходимый уровень.

**Затронутые бизнес-сценарии:**
- 🔒 Риски утечки персональных данных
- ⚖️ Несоблюдение требований регуляторов
- 🏛️ Риск отзыва банковской лицензии
- 📋 Сложность проведения аудита
- 🚨 Отсутствие оперативного выявления инцидентов безопасности

**Бизнес-impact:**
- Юридические риски, штрафы (до 6% выручки по 152-ФЗ)
- Репутационные потери
- Потеря клиентов и партнеров

## Приоритизация по MoSCoW

### Must Have (Критично для бизнеса)

| Приоритет | Проблема | Обоснование |
|-----------|----------|-------------|
| **M1** | **Низкая производительность аналитических процессов** | Напрямую блокирует достижение целей. Бизнес не может оперативно принимать решения. Влияет на все домены. |
| **M2** | **Отсутствие self-service портала данных** | Ключевое требование бизнеса из ТЗ. Без этого невозможно достичь финального состояния. |
| **M3** | **Недостаточная безопасность и compliance** | Критично для медицинского и финтех-направлений. Риски штрафов и потери лицензий. |
| **M4** | **Отсутствие доменной изоляции** | Блокирует независимое развитие направлений и интеграцию новых бизнесов (фармкомпании, производители оборудования). |

### Should Have (Важно, но не критично)

| Приоритет | Проблема | Обоснование |
|-----------|----------|-------------|
| **S1** | **Монолитное хранилище данных (DWH)** | Первопричина многих проблем. Решается через разделение на домены (связано с M4). |
| **S2** | **Недостаточная масштабируемость инфраструктуры** | Важно для роста, но переезд в облако запланирован. Можно делать постепенно. |
| **S3** | **Отсутствие centralized governance для данных** | Критично для self-service портала, но можно внедрять итеративно. |
| **S4** | **Смешение операционных и аналитических данных** | Важно для compliance и производительности, но можно решать параллельно с другими задачами. |

### Could Have (Желательно)

| Приоритет | Проблема | Обоснование |
|-----------|----------|-------------|
| **C1** | **Устаревший технологический стек** | Важно, но миграция может быть постепенной. PowerBuilder можно заменить для отдельных модулей. |
| **C2** | **Тесная связанность через шину данных** | Желательно решить, но можно работать с существующей интеграцией, постепенно переходя на event-driven. |

### Won't Have (В рамках годового плана не делаем)

*Все выявленные проблемы требуют решения, поэтому категория пустая. Однако полная миграция от legacy может выходить за рамки года.*

## Итоговая приоритизация

### Top 5 проблем для решения в первую очередь:

1. **🔥 Низкая производительность аналитических процессов** (Must Have, Квадрант 1)
   - **Действие**: Миграция критичных датасетов в облачный DWH (Snowflake/BigQuery/Redshift)
   - **Метрика успеха**: Время построения отчетов < 5 минут (вместо часов)
   - **Срок**: 1-2 месяца для MVP
   - **Бизнес-impact**: Прямое влияние на выручку и принятие решений

2. **🔥 Отсутствие self-service портала данных** (Must Have, Квадрант 1)
   - **Действие**: Разработка MVP портала с базовым конструктором отчетов
   - **Метрика успеха**: 80% типовых отчетов создаются без участия IT
   - **Срок**: 2-3 месяца для MVP, 6 месяцев для полной функциональности
   - **Бизнес-impact**: Ключевое требование из ТЗ

3. **🔥 Недостаточная безопасность и compliance** (Must Have, Квадрант 1)
   - **Действие**: Внедрение IAM, RBAC/ABAC, audit logging, шифрование
   - **Метрика успеха**: Прохождение compliance аудита ЦБ РФ и Роскомнадзора
   - **Срок**: 2-3 месяца
   - **Бизнес-impact**: Избежание штрафов до 6% выручки, сохранение банковской лицензии

4. **⚡ Отсутствие доменной изоляции** (Must Have, Квадрант 2)
   - **Действие**: Проектирование и внедрение Data Mesh / Domain-Driven Architecture
   - **Метрика успеха**: Каждый домен может развиваться независимо, время интеграции нового домена < 1 месяца
   - **Срок**: 1-2 месяца проектирование, 6-12 месяцев внедрение
   - **Бизнес-impact**: Обеспечение масштабируемости для новых направлений

5. **⚡ Монолитное хранилище данных** (Should Have, Квадрант 2)
   - **Действие**: Декомпозиция DWH на доменные хранилища
   - **Метрика успеха**: 70% данных перенесено в доменные хранилища
   - **Срок**: 3-12 месяцев
   - **Бизнес-impact**: Устранение узкого горла и повышение гибкости

## Дополнительные рекомендации

### Быстрые победы (Quick Wins) - первые 1-2 месяца:

1. **Внедрить кэширование** для часто запрашиваемых отчетов → улучшит производительность на 30-50%
2. **Создать базовый Data Catalog** (даже в виде wiki) → повысит прозрачность данных
3. **Настроить мониторинг производительности** запросов → выявит критичные bottlenecks
4. **Внедрить базовый IAM** с SSO → улучшит безопасность
5. **Создать pilot для одного домена** (например, финтех) → проверит архитектурный подход

### Риски и митигация:

| Риск | Вероятность | Impact | Митигация |
|------|-------------|--------|-----------|
| Миграция данных приведет к даунтайму | Высокая | Критичный | Использовать CDC (Change Data Capture) для online миграции |
| Сопротивление пользователей к новому порталу | Средняя | Высокий | Обучение, пилотирование с power users, постепенный rollout |
| Превышение бюджета на облако | Средняя | Высокий | FinOps практики, мониторинг затрат, оптимизация запросов |

## Заключение

Приоритизация основана на:
- **Прямом влиянии на выручку и конкурентоспособность**
- **Требованиях регуляторов** (медицинские и финансовые данные)
- **Критичности для достижения бизнес-целей** из ТЗ
- **Блокирующем характере** для других инициатив

Решение первых трех проблем (производительность, self-service портал, безопасность) обеспечит **70% бизнес-ценности** при **40% усилий**, что соответствует принципу Парето.
