# Карта рисков и план управления рисками (Future 2.0)

## 1. Карта рисков

Риски классифицированы на Архитектурные (А), Организационные (О) и Технологические (Т). Оценка вероятности и влияния производится по шкале: Низкая, Средняя, Высокая.

| ID | Тип | Риск | Вероятность | Влияние | Описание |
|---|---|---|---|---|---|
| **R-A1** | А | **Сложность обеспечения согласованности данных** | Высокая | Высокое | Переход на распределенную событийно-ориентированную архитектуру (EDA) и микросервисы усложняет транзакции (CAP-теорема). Риск рассинхронизации данных между доменами (например, Финтех и Медицина). |
| **R-A2** | А | **"Лавинообразный сбой" (Cascading Failure)** | Средняя | Высокое | Тесная интеграция через единую шину событий при отсутствии надежных механизмов изоляции может привести к тому, что сбой в одном сервисе (например, медленный консьюмер) замедлит всю платформу. |
| **R-O1** | О | **Сопротивление изменениям со стороны команд** | Высокая | Среднее | Команды, привыкшие к монолитному DWH и SQL Server, могут саботировать переход на Data Mesh/Streaming и новые инструменты (Kafka, Flink). |
| **R-O2** | О | **Нечеткие границы доменов (Bounded Contexts)** | Средняя | Высокое | Неправильное разделение ответственности между Медициной и Финтехом может привести к созданию "распределенного монолита" и дублированию логики. |
| **R-T1** | Т | **Нехватка компетенций (Skill Gap)** | Высокая | Высокое | Технологии Kafka, Flink, Kubernetes требуют специфических знаний, которых может не быть у текущей команды, работающей на MS SQL/PowerBuilder. |
| **R-T2** | Т | **Vendor Lock-in (привязка к облаку)** | Средняя | Среднее | Глубокая интеграция с проприетарными сервисами облака (Yandex Cloud Functions, MDB) может усложнить миграцию или мультиклауд стратегию. |
| **R-T3** | Т | **Проблемы с миграцией легаси-данных** | Высокая | Среднее | Качество исторических данных в старом DWH может быть низким, что потребует значительных усилий по очистке перед загрузкой в Data Lake. |

## 2. План управления рисками

Меры по снижению рисков разделены на Технические (Т) и Управленческие (У).

### R-A1: Сложность обеспечения согласованности данных
*   **(Т) Использование паттернов Saga и Outbox:** Для реализации распределенных транзакций использовать паттерн Saga (оркестрация или хореография). Для надежной отправки событий из БД — паттерн Transactional Outbox (через CDC/Debezium).
*   **(Т) Идемпотентность:** Проектировать все консьюмеры событий идемпотентными, чтобы избежать дублирования обработки.
*   **(У) Определение SLA на согласованность:** Четко определить для каждого бизнес-процесса требования: где нужна строгая консистентность, а где допустима eventual consistency.

### R-A2: "Лавинообразный сбой"
*   **(Т) Circuit Breaker & Rate Limiting:** Внедрить паттерны прерывания цепи и ограничения нагрузки на API Gateway и межсервисных вызовах.
*   **(Т) Dead Letter Queues (DLQ):** Настроить очереди недоставленных сообщений для ошибочных событий, чтобы не блокировать основной поток обработки.
*   **(Т) Асинхронность:** Максимально использовать асинхронное взаимодействие, чтобы сервисы не ждали ответа синхронно.

### R-O1: Сопротивление изменениям
*   **(У) Создание "Центра компетенций" (CoE):** Сформировать группу экспертов и энтузиастов, которые будут обучать коллег и помогать с внедрением новых практик.
*   **(У) Пилотные проекты:** Начать миграцию с некритичного домена, чтобы показать успех и отработать процессы ("Quick Wins").
*   **(У) Обучение и сертификация:** Организовать курсы по Kafka, Docker, Go/Python для текущих сотрудников.

### R-O2: Нечеткие границы доменов
*   **(У) Event Storming сессии:** Провести серию воркшопов с участием бизнеса и разработчиков для точного определения границ контекстов и потоков данных.
*   **(У) Data Contracts:** Внедрить контракты данных (Data Contracts) между доменами-продюсерами и потребителями данных, чтобы зафиксировать схемы и ответственность.

### R-T1: Нехватка компетенций
*   **(У) Найм экспертов:** Нанять 2-3 сильных Tech Lead / Architect с опытом построения HighLoad систем.
*   **(Т) Использование Managed Services:** На старте максимально использовать управляемые сервисы (Managed Kafka, Managed K8s), чтобы снизить нагрузку на эксплуатацию.

### R-T2: Vendor Lock-in
*   **(Т) Использование открытых стандартов:** Использовать Terraform (IaC) для описания инфраструктуры. Предпочитать Open Source решения (PostgreSQL, Kafka, S3 API), даже если они предоставляются как сервис.
*   **(Т) Контейнеризация:** Вся бизнес-логика должна быть упакована в Docker-контейнеры, работающие в Kubernetes, что обеспечивает переносимость.

### R-T3: Проблемы с миграцией легаси-данных
*   **(Т) Инструменты Data Quality:** Внедрить инструменты (например, Great Expectations, dbt tests) на этапе ETL для автоматической проверки качества данных при миграции.
*   **(У) Стратегия миграции:** Использовать подход "Strangler Fig" (Удушение монолита) — переносить данные и логику постепенно, по одному домену, а не "Big Bang" миграцией.
